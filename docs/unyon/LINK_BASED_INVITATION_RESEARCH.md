# University Admin onboarding without invitation email delivery

Research date: 2026-09-29. Scope: options for onboarding University Admins while deferring Resend. External facts below cite first-party Firebase, Cloudflare, browser, or OWASP documentation; statements about the portal cite repository files. This is research, not an implementation decision.

## Recommendation (judgment)

Use **B: a Super Admin creates an email-bound Invitation and copies its one-time link to the intended University Admin**. The invitee creates or signs in to their own Firebase email/password account, completes Firebase's email verification if needed, and accepts the Invitation. This keeps the current requirement that authority is issued to a *verified email address*, while leaving password choice and custody with the invitee. The portal must verify the Firebase ID token's UID, email, and `email_verified` claim, match the verified email to the pending Invitation, and create or reuse the Portal User with that UID before creating the Appointment. The existing D1 path already implements most of those checks; delivery and UI would need to change. [Domain definition](../../CONTEXT.md#L37), [SRS §3.1](SRS.md#L29), [current acceptance](../../src/features/directory/server/d1-university-admin-invitation-repository.ts#L207), [Firebase ID-token guidance](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

This **avoids Resend for the portal Invitation**. It does **not** remove all email: for a new or unverified Firebase account, `sendEmailVerification` sends a Google-managed verification email, and Firebase's password-reset flow also sends an email if used. Firebase says its client-SDK action emails use Google delivery and have limited template customization. [Firebase verification](https://firebase.google.com/docs/auth/web/manage-users), [Firebase action-link overview](https://firebase.google.com/docs/auth/admin/email-action-links).

## Source facts: current portal

- An Invitation binds an email, role, Member University, inviter, and seven-day expiry; the SRS requires Firebase email/password sign-in and a verified email, and denies portal access without an active Appointment. [SRS §3.1](SRS.md#L29), [domain language](../../CONTEXT.md#L33).
- The current feature generates a 32-byte random token, stores only its SHA-256 hash, puts the raw token in a URL fragment, sends that URL via Resend, and revokes the Invitation if delivery fails. Acceptance requires a verified Firebase ID token; D1 compares its email with the Invitation and conditionally marks the Invitation accepted in the same batch that creates the Appointment. Preview does not consume it; revocation and expiry are checked. [Token generator](../../src/platform/crypto/session-tokens.ts#L5), [invitation feature](../../src/features/directory/server/university-admin-invitations.ts#L214), [D1 acceptance](../../src/features/directory/server/d1-university-admin-invitation-repository.ts#L194), [D1 schema](../../database/d1/migrations/0004_invitations.sql#L1).
- Copy-link onboarding is **not currently usable**: the feature returns an Invitation record without the raw URL, the admin action reports “Invitation sent,” both runtimes inject the Resend delivery adapter, and production environment validation requires `RESEND_API_KEY` and `INVITATION_FROM_EMAIL`. This needs a one-time, authorized link reveal and revised delivery failure/configuration behavior. [Feature return](../../src/features/directory/server/university-admin-invitations.ts#L214), [admin action](../../src/app/portal/universities/invitation-actions.ts#L14), [runtime](../../src/features/directory/server/university-admin-invitation-runtime.ts#L21), [environment check](../../src/shared/config/environment.ts#L105).
- The acceptance UI already offers create-account and sign-in modes, but defaults to create-account. It passes `window.location.href` (including the Invitation fragment) as Firebase's email-verification continue URL. Its unauthenticated preview returns the full invited email, role, university, and expiry to a holder of the token. [Acceptance UI](../../src/features/directory/ui/invitation-acceptance.tsx#L15), [Firebase client adapter](../../src/features/access/client/firebase-auth.ts#L54), [preview response](../../src/app/api/invitations/preview/route.ts#L7).

## Options and tradeoffs

| Option | What Firebase does | Portal/security implications | Assessment |
| --- | --- | --- | --- |
| **A. Super Admin manually creates Firebase email/password account** | A password user can be created in the Firebase console or with Admin `createUser`; Admin `emailVerified` defaults to `false`, but privileged code can set it to `true`. [Firebase web user management](https://firebase.google.com/docs/auth/web/manage-users), [Firebase Admin user management](https://firebase.google.com/docs/auth/admin/manage-users). | The admin must choose/transfer an initial password, or arrange a reset. Setting `emailVerified: true` by administration asserts mailbox ownership without the recipient completing a verification action. Creating a Firebase user alone grants no portal role: D1 still needs a Portal User and Appointment, and no routine University Admin manual-provisioning operation was found. [SRS §4](SRS.md#L103), [account-administration interface](../../src/features/directory/server/account-administration.ts#L47). OWASP advises secure credential provisioning and warns against sending passwords in email. [OWASP secrets guidance](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html), [OWASP reset guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). | Reserve manual account configuration for the first, carefully verified Super Admin or exceptional recovery; avoid as routine University Admin onboarding. |
| **B. Email-bound portal Invitation link, copied by Super Admin** | New invitee uses `createUserWithEmailAndPassword`, then Firebase verification; an existing password account uses `signInWithEmailAndPassword`. New-account creation fails if the account already exists. [Firebase password-auth guide](https://firebase.google.com/docs/auth/web/password-auth), [Firebase JS API](https://firebase.google.com/docs/reference/js/auth). | A forwarded link by itself cannot assign the Appointment to a different verified Firebase email under the current D1 check. It is still a sensitive capability: someone controlling the bound Firebase account/mailbox and the link can accept it. Existing verified users need no new verification email; unverified users do. [D1 acceptance](../../src/features/directory/server/d1-university-admin-invitation-repository.ts#L207), [Firebase verification](https://firebase.google.com/docs/auth/web/manage-users). | Best fit with current domain and SRS; manual chat delivery replaces the Resend send step, not identity verification. |
| **C. Admin creates Firebase user; invitee gets password-reset/setup link** | Admin `generatePasswordResetLink` produces a link for an **existing** Firebase user; it does **not send** that link. A separate Firebase client `sendPasswordResetEmail` or Firebase-console action can send a Google-managed reset email. Email verification is a distinct Firebase action with a separate verification link. [Admin action links](https://firebase.google.com/docs/auth/admin/email-action-links), [web user management](https://firebase.google.com/docs/auth/web/manage-users), [custom action handler](https://firebase.google.com/docs/auth/custom-email-handler). | Copying a reset link into chat replaces password handoff with a bearer setup secret; whoever obtains it may set the password. Do not assume a password reset sets `emailVerified`: Firebase documents reset and verification as different action types, and the portal requires `email_verified`. Generating or sharing an email-verification link through chat would let a link holder satisfy verification without demonstrating mailbox control. [Firebase action types](https://firebase.google.com/docs/auth/custom-email-handler), [portal verifier](../../src/platform/firebase/identity-verifier.ts#L68), [SRS §3.1](SRS.md#L29). Admin SDK user management also requires privileged service-account access. [Firebase Admin user management](https://firebase.google.com/docs/auth/admin/manage-users). | More moving parts than B; use only if there is a deliberate reason to provision Firebase identities before users arrive. Prefer Firebase-sent reset and verification emails if chosen. |

**Do not conflate B with Firebase email-link sign-in.** Firebase's passwordless email-link provider is separate, must be enabled along with Email/Password, sends a Firebase sign-in email, and would change the SRS password requirement. Firebase currently lists 5 email-link sign-in emails/day on Spark, versus 1,000 address-verification emails/day; quotas can change. [Firebase email-link setup](https://firebase.google.com/docs/auth/web/email-link-auth), [Firebase limits](https://firebase.google.com/docs/auth/limits), [SRS §3.1](SRS.md#L29).

## `workers.dev` verification continue URL: direct answer

**Yes, in principle, the configured HTTPS Worker origin can be the `ActionCodeSettings.url` continue URL for Firebase's built-in verification email.** The repo's preview origin is `https://unyon-mindanao-portal-preview.tatelgabrielle19.workers.dev`; Cloudflare documents the `worker.account.workers.dev` route, and Firebase permits a web continue URL whose domain is in Auth's Authorized domains. A custom Firebase Hosting domain or custom email handler is **not required** for this web flow: Firebase's default email action handler lives on the project's Firebase Hosting domain and can return to the approved Worker URL. This is a documentation-based conclusion, **not confirmation that this project's Firebase console currently accepts or has registered the host**. [Worker origin](../../wrangler.jsonc#L13), [Cloudflare `workers.dev` routing](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/), [Firebase continue-URL setup](https://firebase.google.com/docs/auth/web/passing-state-in-email-actions), [Firebase default handler](https://firebase.google.com/docs/auth/custom-email-handler).

Required setup: enable Email/Password in the **same Firebase project** used by the web app and server; in Firebase Console **Authentication → Settings → Authorized domains**, add the exact host `unyon-mindanao-portal-preview.tatelgabrielle19.workers.dev` (a hostname, not the full URL or a broad `workers.dev` parent). Supply an HTTPS `ActionCodeSettings.url` under that host, such as a token-free `/sign-in` or a dedicated return page. Keep the Firebase `authDomain` configured for Firebase's action handler; it is a different setting from the portal continue URL. Test one real verification email against the deployed preview before relying on this: no authenticated console state or live send was inspected here. Firebase says `localhost` is no longer automatically authorized for projects created after 2025-04-28, so local non-emulator testing may require a separate Authorized domains entry. [Firebase password provider](https://firebase.google.com/docs/auth/web/password-auth), [Firebase authorized domains and web action behavior](https://firebase.google.com/docs/auth/web/passing-state-in-email-actions), [Firebase default handler](https://firebase.google.com/docs/auth/custom-email-handler), [Firebase localhost note](https://firebase.google.com/docs/auth/web/email-link-auth), [portal Firebase configuration](../../src/features/access/client/firebase-auth.ts#L15), [environment HTTPS rule](../../src/shared/config/environment.ts#L20).

## Link-handling safeguards (facts and recommendations)

- **Source fact:** Browsers do not send the URL fragment in the initial HTTP request or the `Referer` header. That protects the current `#token` from ordinary Worker request and referrer logs, but not from the person or chat service that receives the full pasted URL. Slack documents that it crawls posted URLs for previews; Microsoft Safe Links documents scanning and rewriting links in messages. [MDN fragments](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment), [MDN Referer](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referer), [Slack unfurling](https://docs.slack.dev/messaging/unfurling-links-in-messages/), [Microsoft Safe Links](https://learn.microsoft.com/en-us/defender-office-365/safe-links-about).
- **Recommendation:** Never consume an Invitation on page load, GET, or preview. Keep redemption as an explicit POST after verified Firebase sign-in; retain random high-entropy, hashed, single-use, expiring and revocable tokens, atomic acceptance, and non-cached preview responses. This matches OWASP's guidance for analogous account-recovery links and the current portal pattern. [OWASP forgot-password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [current routes](../../src/app/api/invitations/preview/route.ts#L7), [accept route](../../src/app/api/invitations/accept/route.ts#L31), [D1 acceptance](../../src/features/directory/server/d1-university-admin-invitation-repository.ts#L245).
- **Recommendation:** Do not pass `window.location.href` with the Invitation fragment to Firebase verification. Firebase places the continue URL inside its email-action link as `continueUrl`, so the current code copies the portal token into another URL and email. Use a token-free return URL and tell the user to reopen the original Invitation after verification, or design a carefully bounded same-browser resume path. Consider removing the fragment from browser history immediately after reading it and a `Referrer-Policy: no-referrer` on the acceptance page as defense in depth; the fragment itself is already excluded from browser referrers. [Current code](../../src/features/directory/ui/invitation-acceptance.tsx#L51), [Firebase continue-URL mechanics](https://firebase.google.com/docs/auth/web/passing-state-in-email-actions), [MDN history replacement](https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState), [MDN referrer policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy).

## Initial Super Admin bootstrap and implementation gaps

The proposed **manual initial Super Admin** is separate from routine University Admin invitations. The existing `bootstrap:super-admin` command uses Prisma/PostgreSQL; `bootstrap:local:d1` uses only a loopback Firebase Auth Emulator and local D1. A `D1SuperAdminBootstrapRepository` exists and is wired into D1 access persistence, but this inspection found **no production/remote-D1 bootstrap command or workflow that invokes it**. Therefore manually creating the first Firebase Super Admin account is insufficient to grant portal access on the target D1 path until a controlled production D1 bootstrap path is implemented and verified. [Command scripts](../../package.json#L40), [Prisma bootstrap](../../scripts/bootstrap-super-admin.ts#L6), [local-only D1 bootstrap](../../scripts/bootstrap-local-super-admin.ts#L15), [D1 repository](../../src/features/access/server/d1-super-admin-bootstrap.ts#L18), [D1 wiring](../../src/features/access/server/d1-persistence.ts#L11), [session authorization](../../src/features/access/server/session-service.ts#L64).

For B, implementation work remains to change the invitation delivery interface/UI and production env validation, decide how to reveal a raw link once (the hash-only record cannot reproduce it), remove the token from Firebase's continue URL, and update the Implementation Plan's email-delivery step. No product code was changed by this research. [Current interface](../../src/platform/email/contracts.ts#L3), [current flow](../../src/features/directory/server/university-admin-invitations.ts#L214), [environment](../../src/shared/config/environment.ts#L105), [Implementation Plan §6](IMPLEMENTATION_PLAN.md#L179).
